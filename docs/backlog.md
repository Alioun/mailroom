# Backlog sorting, protocol MOVE and Gmail labels

The local interface previews filing changes against saved rules. Real-account writes remain denied. Legacy synthetic histories and the protocol MOVE journal are separate. Protocol execution requires an explicitly installed, account-bound loopback source and separately installed synthetic workspace evidence. HTTP requests and recovered data cannot install either authority.

## Scope and proof

The default scope is Inbox plus unfiled mail. Gmail's legacy synthetic adapter treats messages without a user label as unfiled. Protocol mailbox.org execution requires an acquired Archive special-use role. Names alone do not establish that role. Inbox-only and Advanced every-folder scopes are available. Sent, Drafts, Spam and Trash remain excluded. Flagged messages are protected by default, and protocol filing excludes preexisting Deleted messages.

Protocol preview resolves the saved workspace through `Accounts::workspace_context`. It retains the exact compiled artifact, executable and saved proof receipt, including pins, as-of and the selected Current or Previous baseline. A separate execution proof evaluates that same parsed artifact against fresh TLS observations. Ordinary IMAP headers and write permission grant no recipient or delivery-envelope authority. Without usable independent evidence, the proof cannot authorize a move.

Filing projects only the proof's destination decisions. Predicted accounting copies, read changes and keywords do not execute. Preview includes destination selections, counts, exclusions and diagnostic reasons. Missing destinations never cause CREATE.

A purpose-specific HMAC binds the exact approval to the saved proof, execution proof, material account state, options, sparse UIDs, topology and installed authority. Source identity includes the account, login, loopback endpoint, TLS name/root, profile and epoch. Runtime authority also binds credential generation, local keys, recovery identity and workspace context. Material changes invalidate continuation without rewriting historical artifacts or operation IDs. Sieve-download receipts cannot start filing or Undo.

## Protocol journal and execution

`AccountState::protocol_backlog` owns schema15 `Journal`, `Run` and `SavedPlan` records. Each batch reuses the validated `MoveEvidence` model. Approval consumption and exact membership persist before execution. The worker then saves attempted Intent before transmission, validated COPYUID mapping before later response processing, completion or loss, and identity readback as distinct evidence. Each command contains at most 500 distinct approved UIDs. Sparse sets never expand to include other messages.

The verified-TLS transport requires MOVE, usable UIDPLUS, stable mailbox identities and writable selected mailboxes. It emits UID MOVE with exact quoted wire names. It never uses COPY, STORE, EXPUNGE, CLOSE or CREATE. There is one execution connection per worker. Local account admission and store locks exclude competing application work.

An entry is verified only when a compatible validated mapping identifies the destination, the source UID is absent and mapped destination readback matches. Tagged OK, source absence, UIDNEXT, counts and Message-ID matching cannot replace COPYUID. A partial mapping resolves only its mapped entries. Missing mapping after possible transmission remains uncertain even if the source is still present. The worker never repeats an attempted MOVE automatically.

Cancel signals active socket work, joins the worker and saves Stop before returning. It stops new batches and retains completed or uncertain effects. Cancel remains available with an invalid ledger and creates no Undo. Status, refresh and process replacement do not resume work. Explicit Reconcile observes only attempts that have no saved readback. Saved readback, including each verified entry of a partially mapped batch, is never replaced by a later observation. Repeated reconciliation therefore adds no evidence and no journal revision. Explicit Resume can execute only the compatible, never-attempted remainder. Unresolved attempted work blocks it.

Conditional Undo has a separate exact preview and initially unchecked confirmation. It reverses verified entries still at their recorded destination while the original mailbox instance remains compatible. In a partially mapped batch only the verified entries are eligible, and the unmapped entries count as conflicts. Undo stays unavailable while any attempted batch lacks saved readback, so Reconcile runs first. Missing or moved-away messages remain conflicts without withholding other eligible messages. A run whose forward evidence stays unresolved remains open after Undo and keeps blocking new runs. Reverse MOVE preserves current flags, records newly assigned UIDs and uses the same durable evidence transitions. A potentially effected reverse MOVE cannot repeat. Undo is not snapshot rollback.

IMAP MOVE cannot atomically prevent another client from changing flags after the final read. Local locks do not exclude other clients. Provider durability and external-client races require independent acceptance.

## Persistence, refresh and recovery

Schemas 1 through 14 with absent protocol fields retain legacy history and install no authority. Schema 18 adds the Gmail label journal; see [recovery format](recovery-format.md). Old schema numbers reject new protocol semantics, including nested injection. Schema15 validates journal lengths, identities, batch membership, evidence phases and resource bounds at save and load. Schema 19 replaces the 32-run and 4 MiB journal caps with Q27 retention for MOVE and Gmail label runs. A run stays fully undoable for 90 days from its completion (`completed_at`). After that, the next backlog action replaces its per-message journal with a summary of message and batch counts, applied and restored counts, planned source and destination folders, and the completion and compaction times, and Undo is no longer offered. A run that is uncertain, in conflict, stopped or mid-undo is never compacted. Runs saved before schema 19 get their completion time at the first action under the new rule, so they keep a full 90-day window. Compaction is one save that writes a new base by atomic rename, so a crash leaves the full run or its summary. An Undo confirmed inside the window may still resume after it closes. Each run's journal is bounded by 1,024 batches; up to 512 retained runs and 100,000 summaries are accepted. The UI shows each run's undo deadline in English and German. Old export bytes and compiler/proof version strings remain exact.

The installed TLS fake persists actual messages, flags, UIDVALIDITY and monotonic UIDNEXT independently of the application journal. Its read-only acquisition adapter scans the same mutable state after moves. Refresh preserves workspace, exports, ledger and unrelated histories. The ordinary legacy synthetic scan still uses its separate header fixture.

Single and selected recovery retain populated protocol journals and immutable IDs. Later independent mailbox, send, unsubscribe, Sieve and folder effects remain outside the captured primary state. Restored accounts remain held and install no source or usable approval. Restoration never reconciles, resumes or reverses provider work. New captures use streamed version-3 bundles, which hold a personal-scale account with its journals; see [recovery format](recovery-format.md).

## Gmail labels

Gmail backlog sorting runs over IMAP with X-GM-EXT-1 through `/api/accounts/backlog/gmail`. It uses the same saved-workspace approval, preview, journal, worker, Reconcile, Resume, Cancel, Undo and interface paths as MOVE. It needs an explicitly installed, account-bound loopback label source whose permit is distinct from the MOVE, read and CREATE permits. The source alone grants no recipient authority. Gmail rules never offer a Sieve download, so preview requires a saved proof that is not blocked instead.

Preview reads LIST and requires exactly one selectable `\All` mailbox. It reads All Mail once with ReadOnlyImap, so X-GM-MSGID identifies each message and a duplicate ID fails the observation. X-GM-THRID is never identity. The default scope is Inbox plus mail with no user label. Sent, Drafts, Spam and Trash labels stay excluded, and flagged and Deleted messages stay put. A destination label missing from LIST excludes its changes as `missing_label` with a diagnostic. Labels are created only through approved folder provisioning, which is currently mailbox.org only, so such changes wait.

Each batch holds at most 500 All Mail UIDs for one destination label, with the approved snapshot of each message: X-GM-MSGID, Message-ID hash, size, date, flags and labels. Its steps are fixed at approval. The first adds the destination label to members that lack it with `UID STORE <uids> +X-GM-LABELS ("<label>")`. The second removes only Inbox from members that have it with `UID STORE <uids> -X-GM-LABELS (\Inbox)`. Every store runs with All Mail selected, so removing Inbox keeps the UID. Before each store the members must still match the expected state exactly. The worker saves the attempt before transmission, the tagged completion or loss, then readback, each as separate evidence. It never replaces the label set, removes other labels, sets or clears flags, expunges or creates a label.

Each member's step outcome is `verified` (tagged OK and readback exactly as expected), `changed` (tagged OK, delta present, other client edits seen), `unapplied` (NO or BAD and the delta absent), `uncertain` (lost completion, or NO with the delta present) or `conflict` (tagged OK without the delta, a changed X-GM-MSGID or UIDVALIDITY, or a missing message). Only verified steps let the run continue. A lost acknowledgment stays uncertain after Reconcile and is never retried.

Reconcile observes only attempted steps without saved readback and never rewrites saved readback. Resume runs only never-attempted steps after every attempted step verified. Cancel stops before the next step and keeps completed effects. Undo has its own preview and initially unchecked confirmation. It reverses only applied deltas of messages without uncertain or conflicting steps: Inbox is restored where this run removed it and it is still absent, then the label is removed where this run added it and it is still present. Later labels and flags stay. Labels created or removed elsewhere do not invalidate a run. All Mail, the destination labels, capabilities and namespaces must still match. A refresh scan changes the material binding and blocks continuation and Undo of an earlier run, as for MOVE.

Gmail offers no conditional label store. Another client can change labels or flags between the final read and the store, and the readback then reports `changed` or `conflict`. The Google behaviors the fixture models are unverified: removal with `-X-GM-LABELS`, idempotent additions, modified UTF-7 label encoding and exact case, system label spelling, stable All Mail UIDs after label changes, partial NO results, untagged FETCH rows during STORE, and concurrent edits. Each has a fake-server case.

- `node scripts/verify-gmail-label-backlog.mjs [group ...]` runs the protected saved-workspace flow against the TLS Gmail fake: authority, forward labels, refresh and Undo, a stale preview after another client's flag, SIGKILL boundaries after intent, after the provider effect, after add before readback, after add before remove, after remove before readback and during Undo, live Cancel with 501 messages, missing label and extension, and populated single and selected recovery.
- `node ui/scripts/verify-gmail-label-backlog.mjs` drives the built English and narrow German controls through save, proof, preview, forward, replacement, Reconcile, Undo, live Cancel and explicit Resume.
- `src/acquisition/gmail_backlog/tests.rs` covers lost, partial and BAD responses, races before and after the final read, changed UIDs, label case, missing labels and the 500-UID batch.

## Remaining limits

COPY fallback, Gmail label creation and the separate unchecked unmatched-mail archive offer remain unimplemented. Gmail label execution is fixture-only. Production source installation and actual provider acceptance remain unavailable. Native confirmation, protected Keychain access, independent Sieve execution and whole-personal-workflow readiness are separate gates. Controls support English and narrow German layouts. Backend diagnostic reason codes remain partly English. Local fixture results grant no real-account write authority.
