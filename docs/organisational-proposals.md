# Organisational filing proposals

The saved rule workspace has an Advanced panel for deterministic filing proposals. It reads saved local header observations and proposes exact local rule changes. Acceptance never uploads rules, creates provider folders, forwards mail, changes message flags or moves messages. Saved-account proof retains unknown recipient evidence and no Sieve capabilities.

## Evidence and identity

Only senders whose canonical received records consistently have bulk or platform markers qualify. These classifications are unauthenticated header claims. ESP infrastructure does not identify a service. Mixed, ambiguous or insufficient observations remain unresolved. Sender matching uses one valid raw From mailbox, never a claimed relay original.

An enabled generic preset's Subject predicates can support a category when a strict majority of the sender's messages match. Language variants of a category combine without double-counting messages. Predicates retain the compiler's ASCII casemap. A unique existing folder can support a category only when the preset or existing owner rules already map that exact configured path. Ambiguous categories or folder mappings remain unresolved. An opt-in bundled core provides category sender lists. Its explicit empty seed supplies no reviewed sender domains. There is no fallback category.

Known disabled preset sender IDs use an enabling patch. Unknown senders use `extend_sender` with the exact address and the category's stable `sender.core.*` ID. The review merges selected addresses into that rule's `extend` list. Several senders for one category share one patch and retain separate decisions. Existing owner patch fields and renamed IDs are preserved. Effective owner mappings, including already accepted extensions, prevent duplicate proposals.

Missing, disabled, restricted or replaced category sender lists remain unresolved. Read-marking targets are not extended. A custom inferred folder must match the category's destination. A subject-supported category follows its existing owner destination. Sender-only extensions keep the category rule at its existing priority. Changes to other owner patch fields retain the established override priority. Both proposal forms preserve `NonBulk`, so generated changes cannot take newsletters ahead of bulk filing. No proposal approves invoice senders, assigns a role, changes read state or creates a forwarding target. Existing independent copy rules remain intact.

Generation reuses proof's canonical input selection. Gmail copies deduplicate by message ID, combine placement labels and exclude a message if any copy is Sent. Candidate identity hashes the saved account/provider, exact raw documents, normalized census and versioned acquisition inputs, explicit as-of, pins, baseline, previous recorded artifact when selected, ledger projection, and generator, compiler, evaluator and report/PSL versions. Acquisition IDs and refresh timestamps are normalized away; topology is sorted. Completeness and whether the evidence is current at the explicit as-of remain semantic inputs. No wall-clock call, random acquisition ID, random proposal ID or UI timestamp enters candidate identity. Approval receipts still bind the exact acquisition instance and timestamps.

Account and workspace revision changes invalidate approval without changing a candidate's semantic identity. A source-byte change, acquisition refresh or changed behavior yields a fresh review identity. Rejection stays keyed to the account and sender using the historical `user.organisation.*` key. Rejected observations remain visible as disabled history after evidence changes and cannot be accepted again. A sibling sender in the same category remains independently selectable. Existing exact rejections and standalone-rule history remain readable. Earlier history is retained. At most 64 candidates are offered per generation; additional observations retain an explained limit. The 512-decision bound rejects further decisions instead of pruning history.

## Local review

Selection and confirmation begin unchecked. Changing selection clears review and confirmation. Each candidate shows its exact sender extension or enabling patch, source observations, rationale, uncertainty, earlier rejection count and current/resulting proof. Batch review shows the complete original and resulting documents, the override diff, exact selected changes, folder diff, omissions, pins and warnings.

Empty, duplicate, unknown, altered, wrong-account and conflicting selections reject. Existing additions cannot be overwritten. An extension appends only the approved sender to the existing patch, preserving its other fields. Acceptance leaves the preset's original bytes and ID/major pin intact. The override is serialized through the common typed document model; the full resulting bytes are visible before acceptance. This can change override formatting and comments. Unrelated configuration values remain intact.

Accept and reject use distinct HMAC purposes. Their receipts bind the complete saved state, exact selection and changes, current and resulting proof, raw documents, ledger source version, rejections, baseline, warnings and effects. Key generation and recovery authority enter the existing purpose-binding boundary. Another feature's receipt grants no proposal authority.

The protected account action reloads and reconciles the installed ledger under account, store and ledger locks before regenerating review. The whole-state save atomically records the selected rules and decisions. Rejection changes only proposal bookkeeping. No authoritative ledger or export file is written. Durable state revision consumes approval, so replay and duplicate retries cannot apply twice. A failed request requires a reload before another review.

Compilation errors and failing pins block acceptance. Stale pins warn. After acceptance, the previous proof and download receipt are stale. Run fresh proof over the saved result. The existing recovery hold also blocks proposal confirmation; captured observations cannot resolve it.

## Persistence and verification

Primary proposal explanations use structured data rather than English prose from the server. A subject-majority rationale carries matching and total counts. An existing-folder rationale and each unresolved reason have stable codes. A missing or ambiguous sender is represented separately from an observed address. The interface validates these fields and displays complete English or German messages, including singular counts and localized numbers.

This display metadata does not enter persisted decisions, candidate identities or approval receipts. Proposal semantics is `organisational-filing-v2`. Receipt purposes remain distinct for acceptance and rejection. The changed semantics invalidates older reviews. Acceptance and rejection labels and their effects appear in the selected language. Exact rule documents, proof records and the original bound confirmation text remain available. Technical proof omissions and warnings still retain their original English prose.

Internal schema 9 carries proposal decisions. Schemas 1 through 8 and their recovery bundles remain readable with no invented approvals. Encrypted reopen, rotation, single-account recovery and selected recovery preserve decisions. Restoration creates fresh authority and retains the read-only reconciliation hold.
