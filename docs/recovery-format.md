# Recovery bundle profile

This development profile uses JWE Compact Serialization with `alg=dir` and `enc=A256GCM`. The separately held recovery secret is 32 random bytes, not a human password. The protected header is authenticated as its base64url ASCII representation. The IV is 12 bytes and the tag is 16 bytes. Compression and algorithm negotiation are rejected.

Primary sources read before implementation:

- [RFC 7516, sections 5 and 7.1](https://www.rfc-editor.org/rfc/rfc7516#section-5.1) defines encryption, authenticated header bytes and five-part Compact Serialization.
- [RFC 7518, section 4.5](https://www.rfc-editor.org/rfc/rfc7518#section-4.5) defines direct encryption with the shared key and an empty encrypted-key segment.
- [RFC 7518, section 5.3](https://www.rfc-editor.org/rfc/rfc7518#section-5.3) requires a 96-bit IV and a 128-bit tag for AES GCM.
- [RustCrypto aes-gcm 0.10.3](https://docs.rs/aes-gcm/0.10.3/aes_gcm/) supplies authenticated encryption and decryption. Its documented platform restrictions remain applicable.
- [NamedTempFile](https://docs.rs/tempfile/latest/tempfile/struct.NamedTempFile.html#method.persist_noclobber) documents no-clobber publication. File and parent-directory synchronization are explicit. These checks do not establish arbitrary power-loss durability.

The selected-state payload has version 2. It captures one explicit, sorted set of 1 through 8 accounts and optionally the installed authoritative ledger. Its per-account manifests retain version 1 and describe each account aggregate. Their shared-ledger exclusion refers to that aggregate; only the outer selected-state manifest can include the authoritative file. Existing version-1 single-account bundles remain readable through both restoration paths. Unknown fields, versions, duplicate or overlapping identities and mismatched inventories reject.

Each account manifest names its identity, state schema from versions 1 through 14, generation, revision, capture boundary, exact ciphertext and metadata inventory, key-material roles and lengths, and comparison dependencies. The selected manifest identifies excluded installed accounts. A dependency on another member is captured; other dependencies remain unavailable unless independently installed. Required decryption and stable-identity material stays inside authenticated ciphertext. Provider passwords and external mailbox, send and unsubscribe stores are absent. No ledger is reconstructed from account projections.

The maximum encoded bundle is 24 MiB. Decrypted JSON is limited to 16 MiB, including all accounts and JSON encoding overhead. Each account ciphertext is limited to 8 MiB, metadata to 4 KiB, account dependencies to 64, and excluded account IDs to 64. The ledger is limited to 1 MiB and its existing version-1 contract, including its 4,000-entry bound. Restore transaction metadata is limited to 256 KiB. These limits can reject captures below the sum of individual resource limits.

Capture acquires lifecycle and store locks in sorted account order. The installed ledger guard binds exact source bytes even when inclusion is unchecked. Every member version, selected and excluded set, ledger choice, source version, capture time and semantics enters a purpose-specific, single-use confirmation. Confirmation recomputes the complete snapshot. Source stores remain locked while the ledger is checked again under its guard before encrypted staging and no-clobber durable publication. Capture success follows file and directory synchronization. Interrupted staging cannot replace any usable bundle. Orphan encrypted stages and unknown files remain preserved.

Restoration supports absent accounts only. It authenticates every manifest, account ciphertext, key and optional ledger before publishing target resources. Every account collision rejects before the transaction starts. Included ledger restoration requires a separate, initially unchecked choice and confirmation of its absent or byte-identical target. A differing current or newly edited ledger rejects. Excluding the ledger preserves the target, including arbitrary owner edits. Exact bytes preserve formatting, comments, notes, associations and unknown fields. Only the installed ledger adapter supplies the source and destination; HTTP callers cannot provide paths.

One durable `recovery-selected.restore` record owns the selected transaction. A stable installation lock coordinates restoration and account creation across processes, including disjoint selected sets. The exact target ledger absence or content version enters the preview even when preservation is selected. The encrypted bundle is staged before that record. Normal account work is denied while it exists, including after one account publishes metadata. Restart reauthenticates the staged bundle and preflights the complete set before resuming. Account credentials and ciphertext must be absent or exactly attributable to this transaction. Ledger publication uses a private, synced file and an exclusive atomic rename. It never replaces an existing owner target. A private plaintext ledger publication file may survive an interruption; the durable recovery staging bundle remains encrypted. Unknown stages are never deleted. Exclusive rename avoids a two-link crash window and rejects unsupported filesystems. Locks and their inodes survive, with explicit OS-lock release.

The marker clears only after the entire selected state is durable. Fresh authority invalidates old approvals while stable account, subscription, operation and effect identities, generations and primary ciphertext survive. Provider evidence is stale. All restored accounts remain read-only pending later authoritative provider reconciliation. Historical completion never authorizes retry or compensation. Production routes deny before repository, credential or native access. Protected executable continuity, authenticated native IPC and Keychain implementation remain missing.

Run `CARGO_PROFILE_TEST_OPT_LEVEL=1 node scripts/verify-recovery-selected-state.mjs` with the verified fake stopped, then `node ui/scripts/verify-recovery-selected-state.mjs` against its paired metadata. These synthetic checks compare exact ciphertext, authenticated histories, ledger bytes and independent post-capture external effects, including actual process replacement. They do not establish arbitrary power-loss durability, provider reconciliation or production recovery readiness.

Internal schema 8 retains bounded versioned read-only acquisition facts. Schemas 1 through 7 remain readable with no invented facts. Capture preserves exact ciphertext. Restored facts remain historical in local account/report views and never clear the restored-account write hold. Outer bundle versions and bounds are unchanged. See [Read-only acquisition evidence](provider-evidence.md).

Internal schema 9 adds bounded exact filing-proposal decisions. Schemas 1 through 8 remain readable without inventing decisions. At introduction new saves wrote 9, and both single and selected recovery validators accept 1 through 14. Capture and rotation preserve decision history. Restored authority invalidates proposal receipts and retains the provider reconciliation hold. Outer bundle versions and limits remain unchanged. See [Organisational filing proposals](organisational-proposals.md).

Internal schema 10 adds bounded versioned ManageSieve attempt and baseline observations. Schemas 1 through 9 decode with absent Sieve facts. New semantics under older schemas reject. Exact captured script bytes survive encrypted rotation/recovery and remain historical under the recovery hold. Outer recovery versions, account counts and resource bounds are unchanged. Capture fails if the existing encrypted resource limit is exceeded. See [ManageSieve discovery](managesieve-discovery.md).

Internal schema 11 adds bounded fixture-owned ManageSieve transaction journals and write invalidation. Schemas 1 through 10 invent no transaction or approval authority. Captured journals remain historical under restored-account holds. Independent provider effects and installed fixture TLS/socket/ownership state stay in the existing synthetic mailbox store and are not rolled back by restoring primary state. See [Fixture-owned ManageSieve transactions](managesieve-transactions.md).

Internal schema 12 adds exact IMAP folder journals and independent synthetic folder topology in the existing mailbox resource. Schemas 1 through 11 invent no provisioning data and reject new folder semantics. Single and selected restoration preserve journals under the existing read-only hold. Restoring primary state cannot resume CREATE or revert later independent folder effects. See [Synthetic IMAP folder provisioning](imap-folder-provisioning.md).

Internal schema 13 adds an optional workspace-context binding to confirmed exports. Older exports default to no binding and cannot serve as usable baselines. Older schemas reject nonempty bindings. Restoration never installs recipient authority from an artifact or export, and its read-only hold remains in force. Both recovery validators accept schemas through 14.

Internal schema 14 adds separately bound current-delivery evidence and synthetic envelope contexts. Schemas 1 through 13 without those fields remain unavailable. Older schema numbers reject new evidence and nested envelope contexts or delivery-tag definitions. Restored data never installs authority, resumes work or lifts the read-only hold. Compiler and proof semantics advance to v4; old exported bytes and version strings remain exact and obsolete baselines remain unusable. Outer versions and resource bounds are unchanged.

Internal schema 15 adds the account-owned protocol MOVE journal. Schemas 1 through 14 without its fields retain legacy history and reject injected protocol semantics. Both single and selected validators use the same journal phase, identity, membership and resource checks. Captured forward and reverse evidence, mappings, executable bytes and operation IDs survive restoration exactly. A bundle cannot install a protocol source, restore a usable approval or lift the read-only hold. Later independent mailbox effects remain preserved. Outer versions and limits are unchanged.
