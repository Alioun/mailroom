# Journaled synthetic backlog sorting

The local account interface previews exact backlog changes against saved rules. Execution is available only for the server's installed synthetic accounts. Every production account-write policy remains denied. The production IMAP adapter still exposes reads only.

The default scope is Inbox plus unfiled mail. Gmail unfiled means no user label. Other accounts require an acquired Archive special-use role. Folder names never establish that role. Inbox-only is available, and every-folder scope is under Advanced. Sent, Drafts, Spam and Trash stay excluded. Unknown non-Inbox folder roles stay excluded. Flagged messages are protected by default. The preview groups destinations with selected checkboxes, counts and top senders, and shows unmatched messages, review counts, exclusions and folders absent from the compiled filing destinations.

The backlog planner consumes the compiled proof's filing decisions. Its concrete changes are separate from the logical proof diff. It never sends accounting copies or changes read flags. The original flags, labels, UIDVALIDITY, UID, Message-ID hash and Gmail ID are included in its plan. Ordinary saved accounts retain unknown recipient evidence. The synthetic account fixture alone supplies synthetic recipient evidence, with fixture addresses under example domains.

A separate HMAC purpose binds confirmation to the whole account state, mailbox revision, immutable compiled artifact, proof/gate, semantics, scope, protections, destination selections and exact operations. Sieve-download receipts cannot start a backlog run. Confirmation persists one prepared run. Replayed or stale requests fail. One unfinished run per account blocks a new run.

Account-state version 3 adds concrete run journals. Versions 1 and 2 migrate without invented runs or approvals. Existing census, workspace and export history survive each writer. Journal records and the synthetic mailbox are authenticated encrypted snapshots in separate directories. The mailbox snapshot also keeps synthetic operation acknowledgments and monotonic per-folder UIDNEXT counters. Emptied folders never reuse an old UID. That acknowledgment is synthetic server evidence, not a real-provider receipt.

Each advance saves batch intent before effects. It processes at most 500 messages with one installed adapter at a time, then persists journal observations. The synthetic mailbox is committed independently of that journal. An interrupted intent becomes uncertain when reopened. Resume first checks the synthetic acknowledgment and its exact destination identity. A missing source without a known acknowledgment never implies success. Identity changes, lost COPYUID evidence and exhausted throttling retain conflicts. Conflict resolution is not implemented, so such a run remains blocked for inspection.

A separate stop operation prevents later batches. A distinct resume request is required to continue it. The final Cancel interaction is deliberately absent while its owner decision is pending. Undo has its own preview and confirmation. It restores only messages still at the recorded identity and destination, preserves current flags and unrelated Gmail labels, and records conflicts. Undo intent and acknowledgments survive retries and restarts. Undo does not promise a mailbox snapshot rollback.

The fake adapter models UID MOVE plus COPYUID, COPY plus UID-specific Deleted and UID EXPUNGE, and Gmail label deltas. It never performs bare EXPUNGE or Gmail expunge. These are persistent synthetic state transitions and command descriptions, not a network IMAP writer. COPY's intermediate protocol phases, real connection lifetime, provider throttling and provider reconciliation remain unverified. New synthetic destination folders are fixture storage behavior, not production folder provisioning.

## Repeatable verification

Run the normal local checks and `node scripts/verify-backlog.mjs` against a synthetic server. `node ui/scripts/verify-backlog.mjs` drives the built interface. With the local port free, `node scripts/verify-backlog-restart.mjs` starts the test-only persistent fake fixture, kills and replaces it before effects, after effects but before journal acknowledgment, after completion and during undo. It verifies both provider shapes, exact recovered effects, repeated resume, flags, labels, encryption markers and the old launch-token rejection. `MAILROOM_BACKLOG_RETAIN=1` keeps the last fake fixture for local inspection. No real account or credential backend is used.

## Incomplete acceptance

Cancel wiring awaits the owner decision. The separate initially unchecked offer for archiving old unmatched mail is not implemented. The fake COPY fallback does not expose crashes between COPY, Deleted and UID EXPUNGE. Real provider adapters, routes, capabilities, recipient provenance, topology, safe write protocols, folder provisioning and live readiness remain unfinished. The existing synthetic census scan still reads an immutable header fixture. Backlog previews and open responses read the independently persisted mutable mailbox. Acquisition refresh from those mutable effects is incomplete. Account forgetting and removal of its journal and fake mailbox are not implemented. Run history caps at 32 runs per account without pruning. Whole-snapshot storage has existing size limits and is not validated at large-mailbox scale. Controls support English and German; diagnostic reason codes and protocol descriptions remain English. No synthetic result completes the personal workflow or authorizes a production write.
