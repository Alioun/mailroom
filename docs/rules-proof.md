# Rules and proof

This unit compiles YAML rules and evaluates the emitted Sieve subset over normalized saved census records. It is a local compiler and proof slice. The complete personal workflow and provider deployment remain unfinished.

## Source model

[The preset](../examples/preset.yaml) and [one override document](../examples/override.yaml) deserialize through one JSON model. Generated structural schemas are in [schemas](../schemas). The compiler then validates semantic constraints such as unique IDs, existing patch targets, folder depth and mailbox syntax. Regenerate schemas with `cargo run --locked --example rules-schema -- schemas`.

Stable IDs have dot-separated components. Overrides pin the preset ID and major version. A known-ID patch can change enabled state, folder, AND conditions, condition extensions, account scope and the read action. Rename chains resolve before patching. Cycles, missing destinations and duplicate migrated patches fail. New rules require an explicit `user.*` ID, category and conditions. Unknown fields fail. The trace and effective metadata retain origins, disabled rules and account scopes.

The generic vocabulary has Money, Contracts, Orders, Travel, Social and Newsletters, with German equivalents. Personal and business roots are configurable. Topic and special folders are direct root children. Overrides select a special folder without renaming a preset topic. Unicode path segments and MIME-encoded Subjects are supported. Sender and Subject comparisons use Sieve's ASCII casemap, so non-ASCII letters do not gain Unicode case folding.

Approved address mappings override exact domain mappings. Ownership confirmation alone assigns no role. Sign-up domains must already have an explicit personal or business role. Active and retired ledger entries generate recipient rules. A new local part on a classified sign-up domain goes to its configured new-address folder. A classified domain outside the sign-up policy sorts normally.

## Bundled category lists

`core_senders: {major: 1}` in the preset selects the bundled CC0 sender release. A preset without this field keeps its authored rules only. The compiler checks the selected major and prepares one stable From rule per category, named `sender.core.money`, `sender.core.contracts`, `sender.core.orders`, `sender.core.travel`, `sender.core.social` and `sender.core.newsletters`.

Each generated rule contains the category's whole domain list, regardless of the census. `sender_set` matches any exact address or domain member. Domain members also match subdomains. Conditions outside the set remain AND constraints. Sender sets support at most 10,000 members and appear only in From rules. An empty set emits no filing effect or destination.

A patch's `extend` adds From addresses and domains as alternatives within an existing sender set. A patch that only extends sender-set membership keeps the From rule's existing priority, so it cannot move ahead of owner filing or mute overrides. Other extensions remain AND constraints. Rules without a sender set keep their existing AND extension behavior. An explicit `when` replaces all conditions. Generated rules include `non_bulk`, so an ordinary category patch does not consume bulk mail before the bulk rule. Disabling, account scope and recipient safety still apply.

The exact release binding, including provenance bytes, enters artifact identity, trace and proposal generation. A changed release therefore requires fresh proof and confirmation. Saved artifacts retain their exact lists. Schema 24 introduces their persisted sender-set tags. The bundled seed is empty and explicitly incomplete. Human-curated rows remain required before this is a useful default catalog.

## Compilation and matching

Role safety runs first. The implemented executable accepts exactly one approved synthetic delivery recipient from Delivered-To or X-Original-To. Unknown roles, missing evidence, multiple recipients and unfiltered roles retain Inbox with internal review status. No Flagged mutation is implied. There is no fallback to To, Cc, relay claims or account ownership.

Forward copies run after role safety and before guards and ordinary filing. Filing then runs guards, user overrides, ledger rules, new-address policy, bulk, From and Subject rules, followed by Inbox retention. One filing action stops execution. Bulk means List-Id or both an exact one-click Post value and an HTTPS URI marker. This is routing evidence, not authenticated unsubscribe authorization.

Named private forwarding targets exist only in the override. Stable forward IDs can be enabled and scoped there. Invoice-address and explicitly approved raw From senders require business eligibility, Message-ID evidence and the copy and duplicate capabilities. Copy intent is grouped by destination before action emission. Later triggers for the same destination explicitly exclude earlier matching triggers. A destination-wide duplicate handle guards later arrivals. Stable rule IDs remain visible, and distinct destinations can each receive a copy. The emitted redirect retains the configured target spelling. Gmail backlog compilation emits no forwards. Keyword forwards require a Subject keyword, nonbulk mail and a PDF or XML part. The compiler emits them only when the engine context advertises the Sieve `mime` extension (RFC 5703), testing `header :mime :anychild :contenttype` for `application/pdf`, `application/xml` or `text/xml`. Without `mime` the whole keyword forward is omitted with a reason. Proof decides the MIME test from the part content types of an acquired original. For any other message the copy is `unknown`, and proof predicts no copy. The engine decides from the delivered message, and a copy never changes filing, so an unknown MIME test does not hold the message for review. Other unsupported required predicates omit the entire rule with a reason.

`CompiledArtifact` has private fields and no deserializer. Its SHA-256 identity binds the compiler semantics version, normalized source documents, account and engine context, scopes, capabilities, effective metadata and executable text. YAML formatting alone does not change its identity. Proof parses the emitted executable into Sieve tests and actions. It never invokes a source rule matcher. A test changes the executable folder and observes the changed decision; an unknown executable action fails.

The parser supports only the emitted subset, not arbitrary Sieve. The compiled Sieve is also the internal matching representation for Gmail backlog decisions. No Gmail XML or Gmail filter deployment is implemented.

## Proof and privacy

`GET /api/sample` returns the complete synthetic request. `POST /api/preview` compiles it. `POST /api/accounts/workspace/save` validates and saves documents, UTC as-of time, census pins and baseline input for the selected account. `POST /api/accounts/proof/preview` proves that saved workspace under the account operation lock without acquiring more mail. Neither route accepts caller engine, context or evidence injection. Ordinary account compilation retains unknown recipient evidence and empty capabilities. Only explicit test fixture construction installs synthetic workspace authority. The former direct account-proof API is removed so every saved-account caller uses the same bound context.

Proof excludes Sent mail and deduplicates Gmail by X-GM-MSGID while combining known placement labels. It returns one filing destination, independent copy eligibility and proposed read status. Counts derive from those displayed decisions. The 13 calendar months include the as-of month. Missing, invalid and future Date values are excluded from those monthly counts and reported. Diagnostics include zero-selected rules, fully shadowed rules, unmatched Inbox senders, partial census and engine omissions.

Pins reference account and Message-ID hash. Missing or cross-account references are stale. Any matching record in the wrong folder fails its pin and blocks the proof. Compile errors reject the request. Stale pins and other diagnostics warn. A warning result never grants deployment authority.

The synthetic library preview can compare current placement or a previous configuration compiled for the same account and engine. Saved-account proof compares current placement or the exact artifact from the last confirmed local export. The alternative comparison has a one-click control. Sensitive decisions and targets stay in the protected local UI response. There is no proof CLI summary or agent export. Existing reviewed census summary and placeholder protections remain intact.

The message list shows at most 50 decisions per page, in proof order. Filters select all messages, Inbox, messages with copies or recipient-review holds. Local search compares subject, sender and destination without changing the proof. Search and filter changes return to the first page; a new proof also starts there. The folder diff follows the displayed messages. Full-census totals, per-rule counts, pins, warnings and approval gates remain unchanged. Empty censuses and filters with no matches have distinct messages. Search text stays in memory and is not saved or sent to the server.

## Durable local workspace and download

The encrypted singleton SQLite row uses account-state version 14. It contains the complete census, an optional workspace, a monotonic account revision and at most eight confirmed export records. The workspace retains raw YAML, its own revision, account-scoped pins, the exact UTC as-of time and baseline mode. Each export retains the exact compiled artifact, source workspace, proof receipt, preparation time and local-download provenance. The private storage decoder restores the immutable artifact without recompiling it. An obsolete semantics version, different engine or changed workspace authority makes a recorded baseline unavailable. Export usability requires the exact current context binding, including account, provider, credential references, key and recovery identities, source identities and installed evidence epoch. Older exports have no binding and remain historical.

Version 1 encrypted SQLite snapshots load with their original census and no invented workspace or approvals. The next successful write migrates them atomically. Unknown versions, invalid JSON and authentication failures retain the existing file. All census checkpoints, refreshes and ownership confirmations preserve workspace and export fields.

An exclusive OS file lock covers the account store's entire lifetime, including validation and replacement. A competing process fails immediately. An empty account-ID lock file remains in the private data directory. Whole-state writes also compare revisions. Census replacement requires loading within that store's lock lifetime. The HTTP workspace save compares the displayed account revision, so a stale tab must reload instead of overwriting a newer scan or save.

`workspace/open` and `workspace/save` accept only the selected account and typed workspace input. Save validates YAML, pin references and proof inputs before replacing a workspace. The UI marks unsaved input and requires an explicit encrypted save before proof. It keeps documents, private targets and receipts out of browser storage.

`proof/preview` reloads the selected account's saved workspace. Its full purpose-separated HMAC binds account, provider, complete census and state revision, raw documents and workspace revision, artifact, compiler and evaluator semantics, pins and expectations, exact UTC as-of, baseline mode and recorded artifact, displayed warnings and gate, filename and exact executable bytes. `proof/download` requires that receipt and explicit confirmation. Under the same account lock it reloads state, recompiles and regenerates the proof, compares the receipt in constant time, then records the baseline before returning the exact bytes. Formatting-only saves, identical census refreshes, pin changes, ownership changes and prior exports invalidate an old receipt.

Only mailbox.org accounts with a nonblocking settled gate can download `rules.sieve`. Failing pins and compile errors block. Stale pins and other diagnostics warn. Gmail backlog can save and prove a workspace but has no Sieve-download action. The browser requires confirmation under the displayed proof. Reload clears local confirmation. A recorded export means bytes were prepared for an owner-confirmed local download. It proves neither filesystem delivery nor provider upload or activation.

Run `node scripts/verify-durable.mjs` and `node ui/scripts/verify-durable.mjs` against the built fake-only server. With that server stopped, `node ui/scripts/verify-durable-restart.mjs` starts and replaces a test-only HTTP process using temporary file-backed fake credentials. It verifies UI recovery, stable proof receipts and bytes, rejected prior launch tokens, and synthetic private-marker absence in encrypted state and metadata. The fixture and credential adapter are excluded from production builds. No real provider or credential store is used.

## Independent synthetic checks

Run `./scripts/verify-sieve.sh`. It generates five variants and 70 independent header fixtures from the public sample, lints each executable with check-sieve and compares Pigeonhole results with fresh-cache evaluator decisions. Variants cover standard rules, German folders with read flags, unknown evidence, Gmail backlog and missing capabilities. Comparisons assert exactly one destination, every copy target and Seen actions.

The runtime image mounts only the synthetic output and the harness, both read-only. Its root filesystem is read-only, temporary writes use tmpfs and networking is disabled. No SMTP or IMAP service starts. Dovecot package installation is confined to image construction and blocks service startup. The synthetic CI workflow runs tests, UI checks and this harness without mail credentials. CI execution itself has not been observed in this local unit.

The verified local tools were check-sieve 1.0.1 at source revision `3a99728878994a7f6f2f14032013fc0f06bacbc1` and Pigeonhole 0.5.19 from Debian Dovecot package `1:2.3.19.1+dfsg1-2.1+deb12u6`. The base image digest is pinned. Apt repositories remain an external version dependency.

Primary tool references:

- [check-sieve usage and supported extensions](https://github.com/dburkart/check-sieve/blob/3a99728878994a7f6f2f14032013fc0f06bacbc1/README.md). It is used for syntax checking, not its experimental simulator.
- [check-sieve MIT license](https://github.com/dburkart/check-sieve/blob/3a99728878994a7f6f2f14032013fc0f06bacbc1/LICENSE).
- [Pigeonhole sieve-test manual](https://github.com/dovecot/pigeonhole/blob/0.5.21/doc/man/sieve-test.1.in). The harness uses simulation and trace output without `-e`. It never sends a message.
- [RFC 5231 section 7](https://www.rfc-editor.org/rfc/rfc5231#section-7) specifies the address count test used by role safety.
- [RFC 7352](https://www.rfc-editor.org/rfc/rfc7352) specifies duplicate state and its prior-execution semantics.

## Incomplete acceptance criteria

1. Real provider recipient evidence, envelope support and capability receipts are unimplemented. Ordinary saved-account proof therefore holds every message. Explicit installed synthetic evidence supports only the fixture recipient profile and grants no provider trust. Multiple same-role recipients are conservatively held too. Full mixed-recipient evaluation remains incomplete.
2. Persistent duplicate-cache true results, cache expiry, concurrent deliveries and actual provider state are not cross-checked. The evaluator starts an empty in-memory cache for each proof and orders messages by parsed Date, UID and stable location. It does not reproduce arrival time or the provider's historical cache. The Pigeonhole harness deliberately checks independent fresh-cache messages only.
3. Keyword forwarding and attachment-dependent rules remain omitted. Provider MIME capability discovery and intake acceptance remain unfinished. [The invoice slice](invoices.md) adds protected refresh-driven reports, synthetic content evidence, exact synthetic send-on, and uncertain recovery. It provides no real sender, native confirmation, SMTP, or accounting acceptance authority.
4. The source schema is a coherent subset of the complete authoring specification. It has no preset forward patches, category-wide enable controls, major-upgrade approval workflow or ledger service, first-seen and leak-report fields. General TOML, Jsonnet, alternative layouts and weak-provider engines remain deferred product scope.
5. [Deterministic organisational proposals](organisational-proposals.md) now support exact rejection and selected local approval over saved observations. Agent export, CLI review and native confirmation remain outside this bounded slice. Proposals infer no roles or invoice-sender approval and never edit external private files.
6. Durable local documents, pins, confirmed Sieve downloads and recorded export comparisons are implemented. [Saved placement comparison](landing-comparison.md) checks recorded version-2 deployments using their exact retained compiled artifact, with an export fallback for older records. Schema 30 saves new deployment artifacts with their confirmed intent, independently of downloads. New-arrival windows and strict/warnings-only advanced gates remain unfinished. Download history records prepared bytes only. It does not prove successful delivery or provider application.
7. Generated ledger, new-address, bulk and unmatched filing rules now have separate diagnostic rows. Omitted rules are reported but engine-gap attribution to individual Inbox messages remains incomplete. Backend diagnostic prose and copy-eligibility states are not fully localized, though controls and proof headings support English and German.
8. T3 preview opened but both snapshot attempts timed out. The actual built UI was verified through the repository's Playwright fallback. T3 preview verification remains unverified.
9. Provider folder separators, existing folder inventory, rule coexistence, accounting acceptance and full-scale census behavior remain unknown. Full Gmail topology and earlier census lifecycle limitations remain as documented in the census receipts. No synthetic check settles these facts.

The [synthetic backlog slice](backlog.md) adds journaled local effects and conditional undo. Production backlog moves, deployment, Gmail forwarding setup, unsubscribe, complete address lifecycle, wind-down reporting and owner-authorized live validation remain later dependencies. Every live-write denial remains enforced.


## Generated filing diagnostics

The proof's `generated_rules` rows come from the parsed emitted executable. Personal and business branches share one row per rule ID. Candidate counts include only messages that clear recipient safety and match that rule before precedence. Selected and monthly counts follow the final filing decisions. A guard or ledger rule can therefore select a message that also counts as a bulk candidate.

The window includes the current calendar month and twelve preceding month buckets, with future, invalid and missing Date values excluded. It is the proof's existing window, not a rolling interval of thirteen months. Each row contains all thirteen buckets, including zeros. The role-safety hold stays in the proof's review count and has no generated filing row. A generated rule omitted from the executable has no row; omission does not mean zero matches. Generated zero or shadowed rows do not add authored-rule warnings or change the proof gate.

## Current-delivery envelope tags

A delivery tag in the existing overrides has a stable ID, an explicit nonempty account scope, an enable flag, an exact `envelope_to` mailbox, and one `add_keyword`. At most 32 tags fit within the existing 200-definition bound. The compiler rejects reserved or colliding IDs and malformed mailboxes or keywords. Keywords are single ASCII IMAP atoms and exclude system flag names. Generated JSON schemas come from `examples/rules-schema.rs`.

Only a separately installed synthetic envelope source enables this path. Ordinary IMAP acquisition records unavailable delivery evidence. IMAP ENVELOPE, To, Cc, Delivered-To, X-Original-To, Received, authentication headers, observed keywords and setup reports cannot establish it. Known evidence binds one recipient to account, provider, source, profile, epoch, credential/key authority and exact message location/hash. Multiple candidates remain ambiguous even when their roles agree. Plus extensions remain part of the exact address.

In envelope mode, role classification, ledger matching and ToAddress conditions all use that same delivery recipient. An address role overrides its domain role. Route membership supplies no role. Parsed predicates use match, no-match and unknown. Negating unknown remains unknown. A required unknown input retains Inbox for review without filing, copies or flag additions. Pins for such messages report unknown rather than pass.

Both `envelope` and `imap4flags` must be present in the installed mailbox-Sieve context to emit a complete tag. Missing evidence, capability or account scope produces a whole-tag omission with a reason. Gmail backlog omits tags and accounting copies. Discovery advertisements do not install authority. Old synthetic header profiles keep their original meaning.

Tags emit nonterminal `addflag` before the role-safety hold and every delivery action. When verified delivery-envelope evidence matches a tag's address, the keyword is added even if unknown or mixed recipient roles hold the message in Inbox for review. Proof reports this as `held_tagged`. The hold keeps Inbox placement and read status unchanged, adds no Seen and creates no accounting copies. The keyword records ingress only and grants no role, filing authority or accounting eligibility. Different, unavailable, ambiguous, unsupported and incompatible evidence keep their own outcomes and add no keyword on held or eligible mail. Header observations never count as envelope evidence, and missing evidence or capabilities never produce the tag through a fallback. Tags create no folders, copies, stop or keep actions. Existing approved mark-read rules remain independent.

Sieve accumulated flags start empty. Proof displays observed IMAP flags separately from planned keyword additions and never claims a complete final set when observations are absent. Additions compare case-insensitively and preserve unrelated observed metadata. The prediction does not mutate stored mail. Successful CHECKSCRIPT or activation does not prove permanent keyword storage. An ingress-address match does not authenticate Gmail as sender.

Compiler semantics are `mailroom-sieve-subset-v6`. Parsed proof semantics are `parsed-emitted-sieve-subset-v6`. Version 6 adds the MIME content-type test for keyword forwards; artifacts compiled without `mime` emit the same bytes as version 5. Version 5 exports become previous, unusable baselines without recompilation. Version 5 moved tags ahead of the role-safety hold. Version 4 exports keep their exact bytes, version strings and held-mail behavior, and become previous, unusable baselines without recompilation. Historical exports keep exact bytes and original version strings. Old semantics remain unusable as current baselines. All saved proof, download, ledger, proposals, transaction and folder consumers resolve one context through `Accounts::workspace_context` and use the immutable emitted artifact at the current revision.

With port 4173 free, run `CARGO_PROFILE_TEST_OPT_LEVEL=1 node scripts/verify-envelope-keyword.mjs`, then `node ui/scripts/verify-envelope-keyword.mjs`. The HTTP flow saves YAML, proves and confirms exact download bytes, compares them to the candidate stored through verified local TLS, provisions folders from the same artifact and replaces the process with changed or removed sources. The browser flow uses the repository Playwright Chromium workflow on the built English and German interface. Paired identity metadata is `.audit/envelope-keyword-retained.json`. Stop it with `node scripts/verify-envelope-keyword.mjs --stop` before rebuilding. Historical fixtures are retained.

The local TLS fixture stores script bytes. It does not execute Sieve. Independent Docker/Pigeonhole execution remains blocked and must not be inferred from these checks. Provider setup, actual envelope semantics, keyword persistence, native confirmation and personal readiness require later acceptance.

## Cost at personal scale

A proof over a loaded census is remembered for its exact inputs: the SHA-256 of the census JSON and the serialized artifact, date, pins and baselines. A preview and the confirmation that repeats it evaluate a 100,000-message census once. The 13-month candidate counts come from the same pass unless the configuration can copy, since copies enter duplicate state that a pass over only those months would build differently. Bindings that commit to the whole account state (saved-proof receipts, backlog start and undo receipts, backlog material) serialize the census as its digest, computed once per loaded census. The saved-proof receipt and the backlog receipts moved to `/v2` purposes; a backlog run saved with a `/v1` material is still checked against `/v1`. On aarch64, `.cargo/config.toml` enables the ARMv8 AES and POLYVAL instructions in RustCrypto, which otherwise run constant-time software code. The local launcher builds an optimized binary.
